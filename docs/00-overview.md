# 00 — Overview

> **TaskFlow Pro** — 팀 업무 관리 풀스택 웹앱

---

## 문서 구성 매핑표

| 파일명 | 역할 | 알 수 있는 것 |
|---|---|---|
| `00-overview.md` | 문서 지도 | 전체 문서 구조·읽는 순서·분리 원칙 |
| `01-product.md` | 제품 정의 | 왜 만드는가, 누구를 위한가, 핵심 가치 |
| `02-specs.md` | 기능 명세 | 무엇을 만드는가, 기능 목록·유저 스토리·제약 |
| `03-design.md` | 기술 설계 | 어떻게 만드는가, 아키텍처·폴더 구조·기술 스택 |
| `04-tasks.md` | 작업 계획 | 언제 만드는가, 마일스톤·스프린트·우선순위 |
| `05-conventions.md` | 협업 규칙 | 어떻게 협업하는가, 코딩 컨벤션·브랜치 전략·커밋 규칙 |

---

## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
   (지도)          (목적)         (무엇)         (어떻게)       (언제)         (규칙)
```

새 작업을 시작하기 전에 위 순서대로 읽는다.
앞 문서를 이해하지 않으면 뒤 문서의 결정이 왜 그렇게 내려졌는지 맥락을 잃는다.

---

## 왜 이렇게 나누는가 — 관심사 분리 원칙

코드에서 관심사 분리(Separation of Concerns)가 레이어마다 역할을 고정하듯,
문서도 **한 파일이 한 가지 질문에만 답한다**.

| 질문 | 담당 문서 |
|---|---|
| 왜 존재하는가? | `01-product` |
| 무엇을 하는가? | `02-specs` |
| 어떻게 동작하는가? | `03-design` |
| 언제 완성되는가? | `04-tasks` |
| 어떻게 협업하는가? | `05-conventions` |

### 이 원칙이 주는 실질적 이점

- **변경 범위 최소화** — 기획이 바뀌면 `01-product`만 수정하면 된다. 코드 설계는 건드리지 않아도 된다.
- **탐색 비용 감소** — "API 명세가 어디 있지?"를 고민하지 않는다. `02-specs`를 열면 된다.
- **리뷰 명확화** — PR 리뷰어가 변경된 문서 하나만 읽어도 무엇이 달라졌는지 파악할 수 있다.
- **신규 합류자 온보딩** — 순서대로 읽으면 맥락 없이 코드부터 보는 혼란을 피할 수 있다.
