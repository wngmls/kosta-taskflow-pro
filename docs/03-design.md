# 03 — Design

모든 기술 결정은 아래 표에 사유를 기록한다.
**이 문서에 사유가 없는 의존성은 도입 불가**다.

---

## 기술 결정표

### 1. 백엔드 프레임워크

| 항목 | 내용 |
|---|---|
| **선택** | FastAPI |
| **대안** | Django, Express |
| **근거** | 타입 힌트 기반 자동 문서화(OpenAPI), 비동기 지원, 경량 구조. Django는 ORM·Admin 등 MVP 불필요한 기능이 과도하게 포함됨. Express는 JS 생태계로 Python 백엔드 일관성 깨짐 |
| **트레이드오프** | Django 대비 생태계 성숙도·플러그인 수 적음. 팀이 Python FastAPI 경험 없으면 학습 비용 발생 |

---

### 2. 프론트엔드

| 항목 | 내용 |
|---|---|
| **선택** | Vanilla JS + Tailwind CDN |
| **대안** | React, Vue |
| **근거** | MVP 규모에서 프레임워크 빌드 파이프라인 불필요. CDN 한 줄로 Tailwind 사용 가능, 번들러·설정 0. DOM 직접 제어로 디버깅 단순화 |
| **트레이드오프** | 컴포넌트 재사용·상태 동기화가 수동이라 기능 증가 시 유지보수 부담 상승. 확장(Kanban·실시간) 시점에 React 마이그레이션 검토 필요 |

---

### 3. 데이터베이스

| 항목 | 내용 |
|---|---|
| **선택** | SQLite → PostgreSQL (마이그레이션 경로 확보), ORM: SQLAlchemy |
| **대안** | PostgreSQL 즉시 도입, Prisma, 순수 SQL |
| **근거** | MVP는 단일 사용자·소규모 데이터로 SQLite 충분. SQLAlchemy로 추상화하면 PostgreSQL 전환 시 코드 변경 최소화. 설정·인프라 비용 없이 로컬 개발 가능 |
| **트레이드오프** | SQLite는 동시 쓰기 제한. 팀 기능(다중 사용자) 추가 전 PostgreSQL 전환 필수. 전환 시 마이그레이션 스크립트 작성 필요 |

---

### 4. CSS 방식

| 항목 | 내용 |
|---|---|
| **선택** | Tailwind CSS 단독 사용 |
| **대안** | styled-components, CSS Modules, 순수 CSS |
| **근거** | 유틸리티 클래스로 HTML에서 스타일 의도 즉시 파악 가능. 디자인 토큰(rounded-xl, shadow-lg 등) 일관성 강제. styled-components는 JS 번들 의존으로 Vanilla JS 구조와 충돌 |
| **트레이드오프** | 클래스 문자열이 길어져 HTML 가독성 저하 가능. Tailwind 미숙자는 유틸리티 클래스 학습 필요. **styled-components는 이 프로젝트에서 금지** |

---

### 5. 실시간 처리

| 항목 | 내용 |
|---|---|
| **선택** | MVP: 3초 폴링 (`setInterval` + `GET /api/tasks`) |
| **대안** | WebSocket, SSE(Server-Sent Events) |
| **근거** | MVP는 단일 사용자 시나리오로 실시간성 요구 낮음. 폴링은 구현·디버깅·인프라 비용이 0에 가까움. WebSocket은 연결 관리·재연결 로직·서버 설정 복잡도가 MVP 가치 대비 과도함 |
| **트레이드오프** | 3초 폴링은 불필요한 API 호출 발생. 다중 사용자 시 데이터 충돌 감지 불가. **WebSocket은 팀 기능 추가 시점에 도입** |

---

### 6. 프론트엔드 상태 관리

| 항목 | 내용 |
|---|---|
| **선택** | 모듈 변수 + DOM 직접 갱신 |
| **대안** | Redux, Zustand, Pinia, Context API |
| **근거** | Vanilla JS 환경에서 외부 상태 라이브러리 도입은 번들러 필요. 태스크 목록 단일 배열을 모듈 스코프 변수로 유지하고, 변경 시 DOM을 직접 재렌더링하는 방식으로 충분 |
| **트레이드오프** | 상태와 DOM 간 동기화를 수동으로 관리해야 함. 화면이 복잡해질수록 버그 위험 증가. React 마이그레이션 시 상태 구조 재설계 필요 |

---

### 7. 디자인 시스템

| 항목 | 내용 |
|---|---|
| **선택** | Mac OS UI 톤 기반 자체 토큰 |
| **대안** | Material Design, Ant Design |
| **근거** | Material·Ant는 고유 컴포넌트 라이브러리와 패키지 의존성이 따라옴. MVP 규모에서 Tailwind 토큰만으로 Mac OS 톤 구현 가능 |
| **트레이드오프** | 컴포넌트 직접 구현 부담. 접근성(a11y)·키보드 내비게이션을 수동으로 챙겨야 함 |

**디자인 토큰 (Tailwind 클래스 기준)**

| 토큰 | 클래스 | 용도 |
|---|---|---|
| 모서리 | `rounded-xl` | 카드·버튼·모달 |
| 그림자 | `shadow-lg` | 카드·드롭다운 부상 표현 |
| 반투명 배경 | `backdrop-blur-md` + `bg-white/70` | 카드·헤더 |
| 폰트 | `font-sans` (시스템 폰트 스택) | 전체 |
| 터치 타깃 | 최소 `h-11` (`44px`) | 버튼·아이콘·링크 전체 |

### 8. 테마 (라이트 / 다크)

| 항목 | 내용 |
|---|---|
| **선택** | Tailwind `dark:` 변형 + `localStorage('theme')` |
| **대안** | CSS 변수 수동 전환, prefers-color-scheme 자동 적용 |
| **근거** | Tailwind `dark:` 변형은 `<html class="dark">` 하나로 전체 다크 스타일 전환 가능. `localStorage`로 사용자 선택을 유지해 새로고침 후에도 테마 복원 |
| **트레이드오프** | `prefers-color-scheme` 시스템 설정을 초기값으로 사용하지 않음 — 사용자가 직접 토글해야 적용됨. 시스템 테마 자동 추적이 필요하면 향후 옵션으로 추가 검토 |

**테마 동작 규칙**

```
페이지 로드
  └─ localStorage('theme') 존재?
       ├─ 'dark'  → <html class="dark"> 적용
       ├─ 'light' → class 없음
       └─ 없음    → class 없음 (라이트 기본, 시스템 설정 미반영)

토글 버튼 클릭
  └─ <html> class 토글 + localStorage 갱신
```

> **주의**: `prefers-color-scheme` 의존성은 MVP 범위 외다.
> 추가하려면 이 문서에 사유를 먼저 기록하고 사용자 승인을 받는다.

---

## 의존성 추가 정책

> 이 문서(`03-design.md`)에 **선택 사유가 기록되지 않은 라이브러리·패키지·외부 서비스는 도입 불가**다.
>
> 새 의존성이 필요하면:
> 1. 기존 스택으로 해결 가능한지 먼저 검토
> 2. 불가능하다면 위 결정표 형식으로 사유를 작성
> 3. 사용자 승인 후 도입
